# Полный цикл из панели без постоянного SSH

После однократного включения отдельный native-controller выполняет:

```text
сохранение подготовленного входящего в панели
    → read-only план и проверка владения Host
    → согласование SAN сертификата сайта
    → reload локального Nginx и проверка backend
    → подготовка управляемого Host (выключен, fork-pending)
    → проверка и плавный reload SNI-router
    → публикация управляемого Host
```

Контроллер не вызывает общий `x-ui-fork apply`, не перенумеровывает порты и
не перезапускает панель/Xray. Сама панель может штатно применять конфигурацию
своего входящего при сохранении. Работают systemd, Python 3, Nginx, HAProxy,
OpenSSL, curl и штатный ACME-помощник форка. Docker в этом режиме не поддержан.

## 1. Один раз включить

Сохраните SSH-доступ, рабочую БД и серверное окружение. Получите опубликованное
обновление в каталоге проекта и добавьте в активный `.env`:

```dotenv
XUI_PANEL_CONTROLLER_ENABLE=true
XUI_AUTO_DB_APPLY=false
XUI_HOSTS_SYNC=false
XUI_REWRITE_INBOUNDS=false
```

Для контроллера не нужны списки ID и доменов в окружении. Он задаёт дочерним
помощникам **ограниченный набор из проверенного плана**, а не запускает старую
широкую автоматику. Это явное разрешение сертификатных запросов и настройки
собственных служб сайта/router, даже когда глобальный `XUI_AUTO_CERTS=false`.
Права на остановку чужих веб-серверов при ACME остаются отдельными: без них
контроллер не освобождает занятый HTTP80 самостоятельно.

В этом контексте Certbot запускается без directory-hooks форка, чтобы общий
deploy-hook не перезагружал панель. Контроллер сам обновляет локальный сайт.
Собственные hooks, отдельно заданные администратором в конфигурации его
ACME-клиента, нужно проверить самостоятельно — они вне владения контроллера.

```bash
x-ui-fork backup
git pull --ff-only
x-ui-fork controller plan
x-ui-fork controller install
x-ui-fork controller status
```

`plan` не пишет БД, state или службы; показывает найденные профили и имена
полей, которые потребуют изменения. Для просмотра разрешение ещё не требуется.
`install` запускает только `x-ui-panel-controller.service`, а не панель/Xray.
После установки конфигурация проверяется примерно каждые две секунды; CA и
проверка backend занимают дополнительное время.

## 2. Как настроить входящий в панели

Под управлением только **подготовленные локальные** VLESS/REALITY:

| Поле | Требование |
|---|---|
| Enable | Включён |
| Listen | 127.0.0.1 или ::1 |
| Локальный порт | Свободный 1024–65535, не443 и не локальный HTTPS-порт сайта |
| Транспорт | TCP/RAW, XHTTP/SplitHTTP или gRPC |
| Security | REALITY |
| Reality target | /run/x-ui-selfsteal/https.sock |
| xver | 1 |
| sockopt.acceptProxyProtocol | true |
| serverNames | Ваши различные валидные DNS-имена |

Для XHTTP/gRPC задайте корректные path/serviceName и совместимые параметры
клиента; Vision у XHTTP должен быть выключен средствами панели. Контроллер не
исправляет Flow, ключи, UUID, маршрутизацию, listen и локальный порт за вас.
Публичные/прямые REALITY-профили остаются вне его управления. Неправильно
подготовленный локальный профиль или повторяющийся SNI останавливает проход,
а не переназначается другому входящему.

**DNS нужно подготовить заранее.** Наличие имени во входящем не создаёт запись
у DNS-провайдера. Должны работать A/AAAA, маршрутизация на сервер и HTTP-01 либо
заранее настроенный другой ACME-метод. Контроллер не хранит API-токен DNS.

## 3. Какие Hosts принадлежат контроллеру

- Созданный им Host получает тег **fork-managed**. Адрес/SNI берутся из
  serverNames, внешний порт443, security=reality. Path/Host header — из
  транспорта; fingerprint/ALPN — только явно заданные значения. Догадок
  Firefox/Chrome/http/1.1/h2 нет.
- Существующий **ручной** Host без этого тега не переписывается и не удаляется.
  Если у него уже совпадают входящий, SNI и внешний443, используется read-only,
  без создания активного дубля.
- Если хотите управлять существующим Host, **явно добавьте тег fork-managed
  в панели**. Поддерживаются tags как JSON-массив и как список через запятую.
  Контроллер не добавляет этот тег ручным строкам сам.
- Явно выключенный managed Host не включается автоматически. Временно созданный
  самим контроллером Host отличим по тегу **fork-pending**: он выключен до
  успешного router apply. Ручные выключенные Hosts с похожим текстом тегов не
  считаются pending.
- При одном managed Host и смене единственного домена обновляется тот же Host.
  Сложное удаление имён/профилей и очистка старых неоднозначных managed строк
  требуют ручной проверки: автоматического DELETE/сборщика мусора нет.

Сохраните входящий — следующий проход согласует изменения. Обновите таблицу
Hosts в браузере и подписку на клиенте. Уже импортированные профили клиента
не изменяются сами. Контроллер пишет БД и не умеет инвалидировать неизвестный
внутренний кеш сторонней сборки панели; это нужно проверить на вашей версии.

## 4. Ошибки не должны публиковать неработающие новые профили

- Ошибка DNS/ACME/site/backend до staging оставляет Hosts без изменений.
- Перед публикацией источник перечитывается под блокировкой SQLite. Замена БД,
  новая правка формы, timestamp или снятие ownership прекращают устаревший проход.
- При ошибке router существующие изменённые managed строки откатываются **только
  если они всё ещё равны нашей подготовке**. Пользовательская правка не затирается.
  Новые строки остаются выключенными/pending для повторной попытки.
- Полной транзакции между CA, Nginx, HAProxy и SQLite нет. Уже выпущенный сертификат
  не удаляется при последующей ошибке; успешный внешний reload нельзя откатить
  SQLite-транзакцией. При падении процесса возможны pending-строки; следующий
  проход их перепроверяет. Во время восстановления БД остановите worker.
- На неизменившейся ошибочной конфигурации повторы идут с паузой 5–300 секунд,
  чтобы не дёргать службы и CA каждую секунду. Certbot сохраняет свои lock/cooldown.
- Изменение только клиентского fingerprint/ALPN не вызывает CA или reload служб.
  Совпадающие значения не записываются заново. Счётчики трафика up/down не
  блокируют согласование, а конфигурационные изменения проверяются.

## 5. Журнал, остановка и границы

```bash
x-ui-fork controller log
x-ui-fork controller plan
x-ui-fork controller once
x-ui-fork controller stop
```

`once` требует включённого разрешения; `stop` останавливает только worker и не
откатывает рабочие Hosts, сертификаты или router. Для постоянного отключения
задайте флаг false и выполните `controller install` либо `stop`.

State хранится атомарно в `/var/lib/x-ui-panel-controller` с правами0700/0600:
только отпечатки публичной конфигурации и идентификатор файла БД, не ключи и
не клиентские UUID. Полные stream JSON и вывод внешних сертификатных программ
в журнал controller не печатаются. При certificate-phase error сначала
проверьте DNS/HTTP80 и штатный журнал Certbot; для локальной диагностики доступна
явная команда `x-ui-fork selfsteal certificate`.

Не включайте широкие AUTO_DB_APPLY/HOSTS_SYNC/REWRITE_INBOUNDS ради этого режима.
Если отдельно используется живое наследование TLS полей, не назначайте ему те
же managed строки без необходимости: это лишний конкурирующий писатель.
Схема не гарантирует обход ТСПУ, не исправляет блокировку IP и не заменяет
настоящую клиентскую проверку и резервную копию перед изменениями.
